# Positioning a 100,000-package harness library

Kind: dated competitor and business research, read September 22, 2026 in United States Eastern time. This is a proposal for the existing [roadmap](../roadmap/roadmap.yaml), especially S-6.40, S-6.45, S-6.52, D-17 and D-23. It does not approve intelligence, set a new price, buy advertising or claim a customer outcome. Vendor descriptions and prices below come from their own sites or repositories, checked on this date. A vendor's own performance figure is a vendor claim, not a Baltor comparison.

## The customer's job and the market verdict

A developer, team or agentic system needs the **right runnable material for one task step**, can tell where it came from and what it may do, can load it in the harness already in use, and can determine whether it helped finish accepted work. A search result, copied file or large catalogue is only part of that job. The [Agent Skills specification](https://agentskills.io/specification) already supports instructions, scripts, references and assets, with only metadata loaded at startup and other files read as needed.

The 100,000-package target is a **supply and serving target**, not a customer advantage by itself. That is an inference from current substitutes: [Vercel's skills command line tool](https://github.com/vercel-labs/skills/blob/main/README.md) searches, installs, updates and temporarily uses skills across many agents; [GitHub CLI's skill commands](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills) now search, preview, pin, install, update and publish them; and major harnesses load native skills directly. A huge catalogue can make discovery harder if near duplicates, broad descriptions or unsafe code dominate the results. It also creates a continuing review and withdrawal obligation.

Baltor's plausible paid job is **selection plus evidence plus exact native delivery for a focused step under the customer's authority**, followed by an accepted result. This is a hypothesis. The [live customer journey audit](../verification/SAAS-LIVE-READINESS-AND-CUSTOMER-JOURNEY-2026-09-22.md) found 43 packaged single-Markdown skill bodies and no observed outside-user path from hosted download through native use to an independently accepted step. The [100,000-row probe](SAAS-AND-HUNDRED-THOUSAND-EXECUTION-GATES-2026-09-22.md#the-measured-scale-gap) found hard serving limits with synthetic metadata, not 100,000 approved packages. Neither report establishes willingness to pay or task improvement.

## A package needs a reason to exist

The owner's definition includes **any file a supported harness actually picks up** from its working directory or step configuration: scoped instructions, skills with scripts and assets, reusable code, subagent and command definitions, hooks, plugins and protocol server configuration. The [100,000-package supply study](HUNDRED-THOUSAND-HARNESS-INTELLIGENCE-SUPPLY-2026-09-22.md) counts a multi-file method as **one logical package**, with unique source-file count and rendered client variants reported separately. A script beside its skill instructions is useful because it performs a bounded step, not because it increases the headline count.

For each candidate package, ask five buyer questions before a review call:

1. Which concrete task triggers it, and what exact input and accepted output does it handle?
2. What existing native skill, directory result, documentation lookup or code search could meet the need? Is this method materially distinct?
3. Which files must the chosen harness discover or invoke, on which client versions, and with what dependencies and effects?
4. What known-wrong case does the package reject, and who other than its author checked its exact bytes?
5. What measured result would show that selecting it improved a customer's work under the same model, budget and task constraints?

This is an admission and prioritization filter, not a new approval system. The [repository rule](../../AGENTS.md#intelligence-rules) still requires candidate status until independent exact-byte approval. Metadata can guide discovery, but it cannot grant file, network, secret, model or spending authority. The owner can withdraw an approved item.

## Price and operating economics

The [standing owner decision](../../AGENTS.md#decisions-that-stand-until-the-owner-changes-them) sets one Baltor Pro plan at **$29 per month**, free search, one downloaded item as the measured unit and no launch overage billing. Invited beta users are free through an operator entitlement. Treat one downloaded **package version** as one item when its required script and reference files arrive together; charging each member file would punish useful multi-file design. That implementation interpretation needs a contract and customer-facing check. Search quotas discussed in an older implementation plan are proposals, not a replacement for the standing rule.

The paid offer cannot be justified by a count when a customer can use a free directory, a native harness skill, or $10-per-seat documentation retrieval. The buyer must see a repeatable saving in search time, risk, review effort or accepted task work. These are value hypotheses, not current claims. A plausible division is: free search lets the customer see relevant, provenance-bound cards; Pro gives governed exact downloads and release management; the customer pays their own model provider. The free-search and Pro boundary is the standing choice, while the complete governed download experience is still to be proven end to end.

Monthly contribution per paying customer should be recorded as:

**$29 minus payment processing, indexed search and transfer, storage, support, review and refresh amortization, refunds and loss.**

Do not put customer model tokens into Baltor service margin if customers pay their own provider, but show model cost beside the customer's outcome. Review and refresh cannot be silently treated as free just because an existing model subscription is available. Allocate their physical calls, human escalations and withdrawal work per active useful package, then per retained customer. For a hypothetical $60 acquisition cost with a three-month payback target, contribution must average at least $20 per month for a customer retained all three months. This is illustrative arithmetic, not a budget, forecast or recommendation to spend. If measured contribution or retention misses it, reduce service cost, improve task value or change the channel before scaling ads.

The metering and product analytics need separate events for relevant search, selected reference, paid entitlement, exact package download, native placement, discovery, actual use, accepted result and repeat use. Retention and paid conversion should be analyzed by **accepted task cohort and file kind**, not by total catalogue size. A model-adapted wording variant should inherit its canonical method identity and review state; it should not become another saleable package solely to raise the count.

## Acquisition message and channel sequence

Start with a narrow task a customer can recognize: a data cleanup step with a bounded script, a repository repair step with a checked procedure, or a protocol connection whose effects are clear. A page should show the real native layout, source and review record, model and permissions used, result check, failures and limitations. The [live-readiness audit](../verification/SAAS-LIVE-READINESS-AND-CUSTOMER-JOURNEY-2026-09-22.md) still has closed public registration, unavailable checkout and portal, and no outside-user accepted task, so broad paid acquisition would send users to an incomplete journey. D-17 and D-23 own the customer and evidence gates.

Proposed sequence within those roadmap steps:

1. Invite developers already trying to finish one repeated task with Codex, Claude Code, OpenCode or Pi. Observe where they currently find, vet and install material; record the time and failures before presenting Baltor.
2. Publish a few original, independently reviewed example packages and native setup recipes through appropriate open repositories and skill directories. Link to a demonstrable hosted selection and update journey; avoid a mass page per generated package. This is a distribution proposal, not authorization to publish candidates.
3. Ask documentation, harness and model-tool maintainers about integrations that let a customer select an exact reviewed package for one step. Give them provenance, compatibility and withdrawal data. A partnership must add adoption or user value, not just another registry listing.
4. Test small, task-specific acquisition channels only when an invited person can sign in, retrieve, natively load, use and repeat the work. Measure cost per retained paying customer and contribution payback. Keep the [roadmap's](../roadmap/roadmap.yaml) spending and legal gates intact.

Possible invited-beta message, once the recorded native path exists: “Bring your own coding agent and model. Find a reviewed package for the next step, see exactly what it can access, and load only the files that step needs.” The present service has not yet proven every clause as a customer journey, so use it as draft copy.

Possible later paid-acquisition message, only after paired task evidence: “Give each coding step the right instructions and tested tools. Compare the finished work, cost and review record with your usual setup.” Name the exact task and measured result beside this line. Keep the number 100,000 in a catalogue status view with definition and date, rather than making it the main promise or treating it as a proxy for usefulness.

## Four discriminating tests

| Test and roadmap owner | Design and measured result | What would refute the advantage |
|---|---|---|
| Held-out discovery and abstention, S-6.52 and S-6.40 | Freeze real task requests before indexing. Compare Baltor's top results with a native skill-directory workflow and documentation or code search where relevant. Count exact intended-method recall at 3, truly relevant alternatives, no-answer correctness, time to a usable item, and rights or effect errors. Report denominators and misses by file kind. | A larger catalogue lowers relevance or supplies unsafe or unlicensed false positives; customers find an equivalent usable item faster elsewhere. |
| Native package delivery, D-17 and S-6.40 | On clean homes and pinned versions of Codex, Claude Code, OpenCode and Pi, select one package each for instructions, a skill plus script, and a tool or connection where supported. Record exact digest, placement, discovery, loading, invocation and use separately. Repeat with inherited files and a withdrawal during download. | Files are fetched but not loaded, a variant activates the wrong behavior, or a withdrawn package remains available. |
| Incremental accepted work, D-17 and D-23 | Use the same frozen tasks, model route, task budget, permissions and independent evaluator. Compare native harness alone, native harness with a manually found equivalent, and Baltor-selected material. Allocate arms in randomized order with clean workspaces and no cross-arm memory; preserve failed and excluded trials. Report acceptance, elapsed time, physical model use and customer model cost. | Baltor adds steps or review burden without improving accepted work under the customer's constraints. |
| Retained value and unit economics, D-17 and D-23 | With consenting invited users, record the task they returned for, repeated useful downloads, support minutes, service cost and whether the $29 offer is chosen when the paid journey is authorized. Tie any later acquisition cohort to retention and contribution, not clicks. | Users like browsing but do not repeat native use or pay enough to cover ongoing review, support and acquisition. |

The first three tests also separate Baltor's potential sources of value: better content, better discovery and better per-step delivery. A single with/without trial cannot identify which caused the result. Keep the [10,000 and 100,000 active-release gates](SAAS-AND-HUNDRED-THOUSAND-EXECUTION-GATES-2026-09-22.md#launch-sequence-through-existing-roadmap-gates) as engineering milestones; require task evidence before using them as buyer proof.
