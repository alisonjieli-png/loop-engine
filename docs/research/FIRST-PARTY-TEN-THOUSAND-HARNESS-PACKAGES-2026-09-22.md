# First-party path to ten thousand harness intelligence packages

Kind: dated research and candidate-factory proposal. Reviewed September
22, 2026 local time against main `0d1f883`. The owner clarified that the
first 10,000 can be original Baltor intelligence generated start to finish
from its ideation dimensions around occupations, job descriptions, tasks,
companies and projects. This report makes that the **first supply lane**.
External registries and skill packs can remain comparison or later supply
lanes. The [roadmap](../roadmap/roadmap.yaml) remains the task authority,
especially S-6.40, S-6.53, S-6.54, S-6.62, S-6.63 and S-6.45. No model
was called and no candidate was promoted for this research.
The owner's later clarification broadens harness intelligence beyond
Markdown: native instruction files, tools, executable code, protocol
configuration, plugins, references and assets may be candidates when a
client actually discovers or invokes them. See the
[file-kind and admission research](HARNESS-INTELLIGENCE-FILE-KINDS-AND-ADMISSION-2026-09-22.md).
The first three generated batches happen to contain 68 Agent Skills;
that does not make `SKILL.md` the required format for the remaining
library. Count distinct approved logical packages across file kinds,
with physical files and client renderings reported separately.

## The unit worth generating

Generate a **distinct, testable task method**, not a file for every cell
in a Cartesian product. One method has a goal, typed input and output,
preconditions, a procedure or reusable code, allowed effects, a completion
check and known-wrong examples. Occupation, company archetype, project
phase, language, harness and model are applicability or rendering facets
unless one changes that method and its checks. “Reconcile invoice to
purchase order” may serve several finance roles and company sizes as one
method. “Export a payment file” is a different method because its effect,
output contract and approval differ.

The public 10,000 count should mean distinct, approved, active logical
packages. A `SKILL.md` plus scripts is one package with several files.
Rendering that package for Claude Code, Codex, OpenCode and a small local
model creates variants, not new methods. Report candidates, exact approved
versions, physical rendered files, native-loaded versions and helpful
versions separately. The [serving audit](TEN-THOUSAND-SEARCHABLE-HARNESS-FILES-2026-09-22.md)
sets the additional search, grant, read and release tests before claiming
all 10,000 are retrievable.

An occupation grid, generator, reviewer panel and package renderer are
mechanics used by classified Loops. Tags classify material for discovery;
they cannot grant model, file, network, secret, spending or external-effect
authority. The four persistent intelligence layers still own bodies by
meaning. Harness intelligence remains the family built for native clients,
not a fifth layer.

## The repository already has idea seeds, not packages

The packaged [six first-party occupation records](../../src/loop_engine/data/occupation_seeds.yaml)
contain 40 task statements. The existing
[seed generator](../../src/loop_engine/core/seeded_generation.py) emits 327
candidate records: 240 generic task questions, 52 facts and 35 code
**specifications** with no implementation. It does not emit 327 native
skills. The generator is parked on the harness-first main line; importing
it as an active runtime simply because it exists would break that
architecture decision. The live
[capability-needs queue](../../src/loop_engine/core/capability_needs.py)
can turn uncovered combinations, failed steps, expensive repeated work,
changed sources and named customer requests into candidate needs with
acceptance criteria. Use that queue to prioritize genuine gaps.

Current [intelligence tags](../../src/loop_engine/core/intelligence_tagging.py)
cover role, domain, geography, language, sensitivity, authentication and
lifecycle. They do not yet carry task, company archetype, project phase,
seniority, time period, skill level or model identity. The 123 starter
items declare only language and lifecycle, so a role-specific
coverage count cannot be inferred from them. The current hosted
[search path](../../src/loop_engine/core/service_runtime/http.py) indexes
purpose, identity, kind and source layer; it does not use those future
facets. A ten-thousand-item grid must therefore change **candidate design,
catalogue classification and served retrieval** together. Adding tags
without indexing and held-out query checks would create invisible work.

The existing [offline preparer](../../tools/prepare_harness_candidates.py)
accepts at most 5,000 proposals from committed local sources under a root
MIT declaration; per-file rights remain unverified,
emits one plain Markdown body each and splits specifications into 50-row
populations. It does not produce multi-file native Agent Skills packages,
independently judge originality or persist a cross-source campaign cursor.
The [Agent Skills specification](https://agentskills.io/specification)
requires `SKILL.md` frontmatter and permits scripts, references and assets.
Use the preparer as a bounded local prototype, not the claimed 10,000-item
factory.

## A sparse ideation space

The proposed task-method record can draw from these axes without multiplying
every value against every other value:

| Axis | Use in production; when it changes a logical package |
|---|---|
| Need origin | An observed customer task, failed step, expensive operation, source change or measured coverage gap. A synthetic occupation task may seed a hypothesis but does not prove demand. |
| Canonical job and task | Occupation, task statement and work activity identify what people do. Normalize shared methods across occupations before writing. A job-title synonym is a search alias, not another package. |
| Typed work contract | Trigger, input artifact shape, output artifact shape, preconditions, completion check and failure states. A different contract or verifier can justify a distinct method. |
| Company archetype | Industry, size, technical stack and declared regulatory or security posture can change constraints. A named company's private policies belong in its customer-provided, tenant-scoped context, never an invented public file. |
| Project and lifecycle | Research, design, implementation, migration, release, incident, maintenance or audit stage. A distinct stage may need different effects and checks; otherwise it is an applicability facet. |
| Execution and authority | Read-only guidance, deterministic code, networked tool, external mutation, secret or spending. An authority change is a different qualified procedure, not a tag that grants access. |
| Locale, language, harness and model | Usually a translation, format or model-conditioned derivative of one method. A legal or data-rule change can require a separately reviewed method; a different filename alone cannot. |

For first-party task coverage, the
[O*NET 31.0 Database](https://www.onetcenter.org/database.html)
offers 18,838 task-statement rows, occupation codes, detailed work
activities and task ratings. Its [database licence](https://www.onetcenter.org/license_db.html)
allows adaptation of its specified downloadable data under Creative Commons
Attribution 4.0. Use its exact version, credit the U.S. Department of Labor's
Employment and Training Administration, link the licence, identify changes
and avoid implying endorsement. Other website content and tools have
separate terms. [ESCO](https://esco.ec.europa.eu/en/structure-esco-downloadable-datasets)
adds multilingual occupations and skills under its own
[reuse conditions](https://esco.ec.europa.eu/en/use-esco/download/privacy-statement),
including a specified acknowledgement for services and a notice of any
modified version.
The [U.S. Standard Occupational Classification](https://www.bls.gov/soc/)
and [North American Industry Classification System](https://www.census.gov/naics/)
help organize occupations and establishments, respectively. The latter is
not a task list. These sources guide **which problems to examine**. They do
not make a generated procedure correct, useful or endorsed by the source.
Task ratings cover only part of the occupations, and missing demand remains
unknown. Start with O*NET Core tasks and shared detailed activities where
appropriate, then preserve long-tail and multilingual coverage without
claiming every physical or regulated task belongs in a coding harness.

## Proposed first-party candidate record and pipeline

One proposed `task_method_candidate/v1` would bind: need ID and origin;
canonical task and applicability facets; exact input and output contracts;
preconditions and allowed effects; a source/fact pack with rights and
versions; generator model or human producer; native package manifest and
body digests; known-good, known-wrong and ambiguous fixtures; independent
review state; and task-evaluation references. The identity of a method is
the behavior and contract, not the role/title/model labels. This is a
research proposal, not an approved schema or new catalogue store.

```text
Observed need or attributed task seed
  -> search existing approved code, skills and source material first
  -> one canonical method specification with acceptance and effects
  -> candidate generation: when to use, when not to use, procedure,
     references, checks, failure and escalation
  -> exact and semantic duplicate clustering across roles and projects
  -> native package rendering with source and asset digests
  -> rights, format, safety, dependency, secret and effect checks
  -> independently evaluated task fixtures and exact-byte review
  -> approved release with indexed facets and reversible withdrawal
  -> consented native load/use/accepted-work observation
```

A generator may use the owner's configured Claude Code, Codex, Kimi,
GLM or other Ollama routes only within exact model-call and spending
authority. Keep producer model identity, prompt digest, source pack and
every physical call. Do not manufacture a source citation or allow a model
to approve its own output. The [three-family review panel proposed in
S-6.63](../roadmap/roadmap.yaml) needs a malicious **and benign** challenge
set, real-batch sampled adjudication and an error gate before its approvals
can scale. A 30-item pilot demonstrates plumbing; it cannot establish a
rare-error rate. Rights-ambiguous, executable, regulated, credential-bearing
or destructive procedures need stronger checks and sometimes a human
domain reviewer. A text safety scan or high model confidence does not
qualify executable code; Code Intelligence requires source identity,
dependencies, effects, tests, independent verification and a digest.
Even 300 randomly sampled approvals with zero observed defects would put
only about a one-percent upper bound on the sampled stratum's defect rate
at one-sided 95-percent confidence. That is too weak to infer that a
10,000-item catalogue has no defects, and a sample never approves the
unsampled exact bytes. Stratify audits by risk and source, hold a batch
when its measured error rule fires, and require stronger per-item gates for
high-consequence material.

An Agent Skills candidate should include a checked native `SKILL.md`, not
just a free-form essay. Other candidate kinds need their own native
files and activation checks. For example, one original “reconcile supplier
invoice to
purchase order” package can declare input fields, mismatches, approval hold,
duplicate-bank-detail warning and a known-wrong fixture. It can apply to
Accounts Payable in several company archetypes without ten copied files.
An output that authorizes payment would be a separate effectful task with
its own authority; a descriptive skill cannot grant it.

### First candidate briefs to prove distinctness

These are **research examples**, not generated or approved packages. Each
brief would need a source pack, exact contract and negative fixture before
generation. Multiple roles can find the same method through aliases.

| Task method hypothesis | Example source of need and facets | Discriminating acceptance check |
|---|---|---|
| Reconcile two tabular exports | Operations and finance roles; spreadsheet or database input | Mismatched keys, duplicate rows and differing units are reported without silently dropping records. |
| Clean an address field | Data work in customer operations; country is a substantive rule | The output retains the raw value and refuses an unsupported country-specific normalization. |
| Deduplicate customer records | Support and revenue operations; consented tenant schema | Two people who share a name but have different identifiers stay separate. |
| Build an incident timeline | On-call engineering; project incident stage | Every timestamp has a source and clock basis; unsupported causal claims are omitted. |
| Compare a proposed code edit with a typed interface | Software maintenance; repository stack | The check finds a deliberately broken caller and preserves a passing unrelated caller. |
| Migrate a configuration key | Software release; old and new schema versions | Unknown old values are refused, not guessed into the new field. |
| Summarize a research paper for a decision | Analyst role; source and decision purpose | The summary distinguishes measured results, limitations and the writer's inference. |
| Draft a project acceptance checklist | Product or project role; task contract | A known-wrong delivered artifact fails at least one independently executable check. |
| Investigate a failed data pipeline | Data engineering; runtime history available | A planted stale log does not outrank a later successful rerun for the same attempt. |
| Prepare a customer response from approved policy | Support role; tenant-provided policy version | Missing policy or a conflicting customer fact produces a hold, not an invented promise. |

The opportunity queue should mix occupation tasks, user-submitted job
descriptions and project briefs with consent, first-party tested code,
observed searches with no good result, and recurring accepted tasks. Treat
public job postings as leads to investigate, not text to copy into a paid
package. Search for an existing general method before authoring a variant.
For a named company, load only the customer's approved policy or project
material into its own scope; the shared library can contain the general
method without pretending to know that company's rules.

## Evidence against counting generation as quality

The June 2026 version of
[SkillsBench](https://arxiv.org/html/2602.12670v4) tests 87 tasks across
18 matched model-and-harness configurations. Its curated skill condition
raised mean pass rate from 33.9 to 50.5 percent on that task set. In a
separate three-configuration condition where an agent wrote its own pack
before solving, results were 8.1 to 11.5 percentage points below the
no-skill baseline. Its trajectory audit found packs the solver never read,
authoring that displaced solving and confidently wrong instructions. That
condition is **not** the proposed offline Baltor factory with independent
review, so its measured loss must not be projected onto our packages. It
does show why the first campaign must measure native discovery and use,
and why generated prose cannot be its own completion evidence. The same
paper found compact, focused packages more effective than exhaustive ones
within its benchmark.

A preliminary
[software-engineering skills study](https://arxiv.org/abs/2603.15401)
found 39 of 49 tested skills gave zero pass-rate improvement and an average
gain of 1.2 percentage points on its real-world software tasks; three
skills degraded performance. This is an external, task-specific preprint,
not a Baltor result. Its warning for the factory is to test version fit and
the **marginal effect** of a package, not assume that an approved, searchable
file helps every model or task. Safety and rights approval can precede
measured benefit, but the service must label the latter as unmeasured until
a paired no-package test and independent task check exist.

## Quantify the first production experiment

Begin with a stratified campaign of about 1,000 **real candidate methods**:
high-frequency digital tasks across occupations, data-work procedures,
project maintenance, several read-only and effectful risk classes, and
held-back customer-like queries. Freeze the selection rule before reviewing
outcomes. Measure the fraction that are distinct, rights eligible,
native-valid, safe, independently approved, findable, loaded and helpful.
Preserve rejected and duplicate candidates with their reasons.
For benefit evidence, freeze customer-like tasks and independent verifiers
that the generator and reviewers cannot inspect. Run matched no-package,
selected-package and raw-factual-source arms with the same model, harness,
budget and allowed effects. Save all trials, including missing loads and
regressions, and report results by package class and model. A package that
passes rights and safety gates can enter the catalogue with **benefit
unmeasured**; it must not inherit a benefit claim from a different item.

The current catalogue has 43 approved single-Markdown items. If all 43 pass
the proposed distinct native-package gates, 9,957 more approvals are needed
to show 10,000; otherwise the deficit is larger. If the first real campaign
measured a 75 percent approval yield on that conditional baseline,
about 13,276 additional candidates and at least 39,828 three-reviewer
calls would be needed, plus generation, failed calls and re-review. At a
50 percent yield, it would take about 19,914 candidates and 59,742 review
calls. These are **illustrative conditional calculations**, not forecasts
or a model allowance. The current 50-row staging shape would require at
least 266 populations for the 75 percent scenario; it creates a new
isolated database per run through
[the staging command](../../tools/stage_intelligence_candidates.py) and
does not supply a durable campaign cursor.
If only 80 percent of generated drafts pass deterministic prechecks, the
75 percent scenario needs about 16,595 drafts and 332 such populations
before retries. The three-reviewer count assumes three full reviews for
each panel-eligible candidate; refusal and escalation policies may change
actual call counts. These numbers do not prove the proposed sources contain
enough distinct digital task methods. In particular, 18,838 occupation task
rows cannot be converted one-for-one into 18,838 useful harness packages.
If each task row yielded at most one method, that source alone would need
at least 53.1 percent end-to-end conversion from **task rows** to approved
methods for a 10,000-item catalogue, before accounting for physical tasks
and shared methods; that conversion is unmeasured. Customer needs,
project workflows and
verified code can add independent opportunities, but their unique yield
must also be measured.
The first campaign must measure actual yield and review throughput before
promising 1,000 in one week or 10,000 in two more.

Prioritize the next cells by marginal distinct task coverage and real
customer requests, not by which dimension makes the largest file count.
Use the existing `CapabilityNeed` acceptance field so a proposed skill can
be rejected when it does not solve the need. A canonical method shared
across five roles improves coverage for five role searches while counting
once. Model-specific shorter or longer renderings from the
[variant research](MODEL-CONDITIONED-HARNESS-INTELLIGENCE-2026-09-22.md)
also count under that one logical source item, with separate approval.

## Serving and user settings still matter

The [10,000-item serving audit](TEN-THOUSAND-SEARCHABLE-HARNESS-FILES-2026-09-22.md)
finds a 2-megabyte manifest loader limit, per-request index rebuild,
unpaged listing, per-item snapshot grants and a single-Markdown-file
builder. Original generation does not remove those blockers. A role,
company-archetype or project facet helps only if the served retrieval
engine indexes it, applies tenant and effect filters, has a relevance floor
and returns a small selected reference. Body-aware search needs its own
permission test. A customer can narrow the library by task, role, industry,
project stage, harness, licence, reviewed status and allowed effects; the
default should not dump the whole catalogue or pretend a poor match is
useful. Current permissions remain separate from descriptive tags.

The 10,000 package index should remain server-side. The
[native skill format](https://agentskills.io/specification) normally exposes
only name and description until activation and reads the complete skill on
demand. Installing every package into every fresh harness would overload
the exact step context the product is designed to control. Materialize only
the chosen package files after selection and permission checks.

Batch approved exact packages into a versioned release with added,
changed and withdrawn counts. Pin selected bytes for a task; a changed
package needs re-review and a new version. Keep model and harness
renderings tied to that parent. A rollback must respect the durable
withdrawal state even if an older image had granted the item. Show
offered, fetched, loaded, used and independently verified as separate
outcomes. Ten thousand active packages can be a truthful library-size
claim; ten thousand useful packages requires later real-task evidence.
Because customers run downloaded packages locally, the first-party customer
licence must state whether local execution, modification, internal sharing
and use after subscription cancellation are allowed. Server-side withdrawal
can stop later fetches and warn clients about a bad version; it cannot erase
a customer's existing copy. Keep the service's access claim consistent with
that physical limit.
