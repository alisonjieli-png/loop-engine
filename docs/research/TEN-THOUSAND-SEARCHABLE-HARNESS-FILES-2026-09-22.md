Kind: dated source, serving-path and admission audit with proposed gates.

owner-reported live release 13. The public responses independently checked
here do not expose an image digest, so this report does not bind those

## Define the promise before counting

“Ten thousand files” can mean ten thousand raw URLs, generated drafts,
physical rendered files, unique logical packages, approved versions, active
versions, or items a customer can actually fetch. The target worth showing
is **10,000 distinct, rights-eligible, independently approved exact versions
in an active release**, each indexed by its permitted metadata. State
whether all 10,000 are retrievable by an ordinary paying account or only
by an operator qualification account; those are different product claims.
Report
physical files, model-conditioned variants, items offered to a particular
account, native-loaded items and helpful items as separate numbers. One
OpenSpec method rendered for ten harnesses is one method and ten variants;
the [official workflow guide](https://github.com/Fission-AI/OpenSpec/blob/main/docs/supported-tools.md)
describes a small set of core workflows across many client layouts.

Searchability needs two tests: every approved exact identity can be found
offline under an authorized test grant, and held-out natural task queries
return relevant items while no-answer queries may return nothing. Body
retrievability needs a digest-matching read for every approved item in an
isolated host, plus bounded live read checks. Offered, fetched, loaded,
used and independently verified remain different facts. Ten thousand
indexed references are not ten thousand useful or natively loaded skills.

“Fully searchable” needs an explicit product contract. Today the hosted
route indexes purpose, identity, kind and source layer, not body text.
At 10,000, **metadata findability** should let an authorized customer find
an item by exact identity and by a relevant task description. **Body-aware
search**, if offered, is a separate engine choice: index only approved
active body bytes and compare its held-out relevance with metadata-only
search. A metadata-only customer must not infer protected body text from a
snippet, embedding neighbor or score. Search still returns small references
and materializes the complete body only after a current body grant. **Native
readiness** means the exact multi-file package can be loaded in a supported
harness; that is a third claim beyond search and server-side read.

belong to classified Loops. None is another executable graph vertex or an

## Review policy before throughput forecast

Three independent reviewer **processes** can decide exact candidate bytes
under a written policy, but three model votes are not three independent
guarantees. They may share training, provider, prompt, rights blind spots or
prompt-injection errors. [LLM jury research](https://arxiv.org/abs/2607.10139)
studies shared-error floors. For the first 1,000 real candidates, freeze a
gold malicious **and benign** set spanning prompt injection, secret
exposure, nested licence exceptions, misleading source claims, changed
remote behavior, unsafe commands, executable assets and low-value copies.
Record source/body digest, generator identity, exact reviewer model/version,
review prompt digest, all three decisions, abstentions and final decision.
The challenge set tests known attack classes; it does not estimate the
unknown real-batch error rate. Independently adjudicate blinded, stratified
random samples of panel approvals **and refusals**, reporting each stratum's
denominator and uncertainty interval. Hold a batch that exceeds a
predeclared defect gate. Measure false approvals and false refusals by
source and risk class before any automated approval rule becomes active.
Unknown or ambiguous rights,
mutable remote effects and high-risk code go to a human decision.

The reviewer campaign must pin each provider, exact model, output-capacity
source, review prompt, maximum physical calls and total allowance before a
batch. Count failed, refused, retried and abstaining calls against that
allowance; preserve provider-reported usage and unknown cost. A provider
outage or quota boundary pauses the batch with a durable cursor and an
unknown decision, not a synthetic approval, silent model substitution or
fixed-attempt termination. Separate generator, scanner, reviewer and
promoter identities even if the same vendor supplies their models.

[NVIDIA SkillSpector](https://github.com/NVIDIA/SkillSpector) is useful
triage, not a promotion gate by itself. Its documentation says the default
exit code can be zero for both SAFE and CAUTION; inspect structured findings
and scan completeness, including `--fail-on-findings` and
`--fail-on-incomplete` behavior. Its static `--no-llm` mode can still send
dependency coordinates to the OSV advisory service, so the scan's network
authority and privacy path must be explicit. The
[Agent Skills reference validator](https://agentskills.io/specification)
checks format, not factual truth, source rights or safe tool effects. A
random human audit can estimate a review process's defect rate or hold a
batch; it cannot approve exact unsampled items on its own.

Claude's proposed 1,000 in a week followed by 10,000 in the next two weeks
requires, after the first 1,000, roughly **643 newly approved items per day**
for fourteen days. Three reviews per item mean at least 1,929 reviewer
calls per day **if every candidate passes**, before retries, re-review and
rights holds. At a 50 percent accepted yield, review calls would roughly
double. Those are arithmetic lower bounds, not a schedule or a spending
grant. Use the first 1,000 to measure eligible-source yield, median review
latency, false approvals, false refusals, model-call usage, human hours and
release throughput; forecast the next batch from observed values.

## Serving blockers visible before 10,000

| Current boundary at `9cdf99e` | Why it blocks a 10,000-item claim | Smallest discriminating check |
|---|---|---|
| [Host manifest loader](../../src/loop_engine/core/service_runtime/http_entrypoint.py) allows at most 2,000,000 bytes. | The current 43-item manifest is 63,671 bytes, about 1,481 formatted bytes per item. A same-shape 10,000-item manifest would be about 14.8 megabytes and refused before serving; this is an illustrative extrapolation, not a forecast of a redesigned format. | Build a representative 10,000-item exact release and load it under a newly justified bound or a versioned catalogue projection. A larger numeric ceiling alone must still reject oversized or malformed input. |
| [Host release builder](../../tools/build_host_catalogue_manifest.py) accepts one `.md` body path per item and writes a release path from its basename. | Multi-file `SKILL.md`, scripts, assets and native protocol configurations are not represented. Two input basenames can collide in the output mapping. | Admit two distinct same-basename source files and require separate digest-bound output identities or a refusal before write; validate a complete multi-file package. |
| [Served search](../../src/loop_engine/core/service_runtime/http.py) invokes `Retriever(records)` on every request. | Each query enumerates authorized items and rebuilds metadata, full-text search and hash vectors. The 354-query relevance study is not a 10,000-card concurrency or memory study. | Build one approved-only reusable index and run frozen exact-ID, task-language and no-result queries at declared concurrency. Measure build/update cost, p50/p95/p99, memory and relevance. Refuse stale grants at read. |
| [Provisioning list](../../src/loop_engine/core/provisioning_server.py) emits every offered item without paging; [HTTP](../../src/loop_engine/core/service_runtime/http.py) caps a response at 262,144 bytes. | A single 10,000-item list will exceed the response contract and disclose all offered identities at once. | Replace unbounded listing with bounded query or page semantics, entitlement and rate policy; prove no request exceeds its declared window and allowance. A paying user granted all 10,000 bodies may still eventually retrieve them, so avoid an absolute anti-reconstruction claim. |
| [Per-tenant grants](../../src/loop_engine/core/service_runtime/runtime.py) are exact item snapshots. | New accounts copy starter bindings once. Later approved items do not automatically become visible to them. The guarded deployment workflow reapplies manifest grants only for named tenants. | Introduce a versioned “follow approved release” entitlement with sparse explicit denials, or another reviewed policy. Test new/existing accounts, revocation and release change atomically; a removed item remains denied after rollback. |
| [Hosted catalogue checker](../../tools/check_hosted_catalogue.py) runs a few searches and no body reads. | Passing that check does not prove every indexed item is retrievable. | In an isolated host, discover and read all 10,000 exact bodies with digest verification; in production, sample permitted reads without charging an ordinary customer. Record inaccessible and withheld items. |

The current 43 local approved items produce about 120 kilobytes of body
files; extrapolating the same average gives about 28 megabytes for 10,000
bodies. That size may fit a release image, but manifest parsing, indexing,
per-tenant grants, start-up hashing, update frequency and rollback remain
the hard questions. The public `provisioning.list` result and search are
metadata operations; large body loading happens only after exact selection
and reauthorization.

## A release that can grow and withdraw safely

Start with a frozen content-addressed release: one revisioned manifest
listing each approved package and physical file digest, independent review
record, licence and host policy. Build and test it from the exact committed
tree, deploy by image digest, and keep the previous image for rollback as
the existing release policy requires. Index projection is rebuilt from that
authoritative approved release and compared by digest before traffic.
Unknown commits and partial builds are not successes.

The release must distinguish a newly approved item from a withdrawn item.
Today the image packages bodies and the deployment workflow reapplies its
manifest grants. A rollback to an older image could regrant a withdrawn
version. A durable withdrawal decision prevents this only if the old reader
already understands it or refuses an incompatible new record version.
Otherwise block that rollback and choose a compatible recovery image. Test
an actual older image against the changed durable state, along with a licence
change, source deletion, malicious report and a grant revoked after search
but before body fetch. Keep the old bytes as historical evidence without
making them active. An already downloaded body cannot be recalled from a
customer's machine; say so in the client experience.

At 10,000, image-packaged bodies may remain an interim option if a measured
release cycle, memory and rollback drill support it. D-05's durable blob and
record architecture is the longer path. Avoid writing 10,000 body files to
Git on every ingestion run; source revisions, review artifacts and approved
release snapshots need deliberate storage and retention. Every release
should report candidate, approved, active, withdrawn, indexed, offered and
retrievable counts with the same snapshot identity.

## User settings and public interface

The future setup can let a customer select a supported harness, their local
or cloud model route, context budget, permitted effects and an eligible
search policy after each choice has a qualified implementation.
The safe default is a qualified search with a relevance floor and a clear
“no suitable item” result. Advanced engine or model-specific rendering
choices can appear only after those engines and exact derivatives are
qualified. Settings cannot turn a candidate into an approved item, bypass
rights, make an unqualified server executable, or grant a new spending
recipient. The [model-conditioned variant research](MODEL-CONDITIONED-HARNESS-INTELLIGENCE-2026-09-22.md)
keeps one logical item separate from its renderings.

Suggested **future defaults**, subject to the host's stricter grants, are:

| Setting | Proposed first choice and visible user control |
|---|---|
| Library family and review | Harness intelligence with current independent exact-version approval. Unknown licence or review stays withheld. Advanced filters may narrow family, kind, licence and minimum review, never widen the host's authority. |
| Search | Automatic only among qualified retrieval engines, with a measured relevance floor and explicit no-match result. An Advanced view may choose an eligible policy and see why another was excluded. |
| Release | Show the latest approved release for discovery, but pin the exact selected item version and file digests for a running task. Present added, changed and withdrawn items between releases; do not silently swap content mid-run. |
| Native layout | Offer only formats actually loaded in the customer's selected, versioned harness. A generic Markdown file is not proof of a native skill or plugin layout. |
| Effects and credentials | No new file, network, secret, spending or external mutation grant from a library item. The customer's local broker keeps provider keys; a direct-key native profile has visibly weaker controls and requires its own choice. |
| Model-conditioned rendering | Use the canonical approved body until a derivative for the exact route, model and harness has its own qualification. Record any fallback to the full source. |
| Account usage | Show the current body-read allowance and exact metered unit before a download, with no surprise overage. Provider model charges remain the customer's separate account. |

Search results should show purpose, origin, licence, version, digest,
declared effects, review state and whether the item is available for this
client. A customer sees a small relevant list, not 10,000 records dumped
into context. Separate offered, fetched, native-loaded, used and verified
states. Display the account's allowed downloads and model-provider charges
separately. The [later live website check](../verification/LIVE-WEBSITE-POST-RELEASE-13-CHECK-2026-09-22.md)
found the repaired hero public, but invitation requests were still disabled
and root `HEAD` returned 404; these remain onboarding gates before paid
acquisition traffic.

## A 10,000-item qualification campaign

Freeze the population and review policy before the campaign. The 1,000-item
pilot measures rights yield, review errors and throughput; the 10,000 stage
is a new campaign only after those measurements. In an isolated host,
require all of the following before saying “10,000 searchable and
retrievable”:

1. Exactly 10,000 distinct approved active exact versions are present with
   rights evidence, independent review, format, safety and effect decisions.
   Candidate, rejected, withdrawn and duplicate renderings are excluded.
2. Every identity is indexed and can be found by an exact authorized query;
   every body or native package can be fetched byte-for-byte with its digest
   by an authorized test principal. If the public claim says all 10,000 are
   available to a paying customer, prove that with an ordinary paid-account
   grant using a bounded, rate-limited qualification path. An unauthorized
   second tenant and a revoked grant cannot fetch the same bytes.
3. A held-out natural-language population tests recall at three and ten,
   no-answer false references, harmful near-duplicate crowding and task
   relevance. Set thresholds and the selection rule before reading results;
   compare with the smaller approved baseline.
4. Cold and warm p50/p95/p99 search and body latency, index build/update
   time, start-up memory, disk, concurrent requests, failure rate, source
   withdraw latency and response sizes remain inside declared machine
   limits. Report every failed or excluded run.
5. A client on the actual live release can search, select and fetch a
   representative sample under a personal key. Native loading and accepted
   customer task results are reported separately; they are not inferred
   from server reads.
6. A rollback, partial upstream crawl, changed body digest and withdrawal
   drill refuse stale content rather than silently reviving it. The next
   release record names the image digest, catalogue snapshot and prior image.

The first imported source and panel can be useful before ten thousand. The
claim becomes a product fact only when the complete denominator passes the
serving, rights and retrieval gates on the same release. S-6.40 owns the
candidate factory, S-6.45 rights and safety admission, S-6.32 relevance,
S-6.39 disclosure limits, S-6.44 native layouts, D-05 durable catalogue
and S-6.35 release checks. The
[million-scale record](MILLION-SCALE-HARNESS-INTELLIGENCE-ADMISSION-2026-09-22.md)
extends the same distinctions beyond this first 10,000-item milestone.
