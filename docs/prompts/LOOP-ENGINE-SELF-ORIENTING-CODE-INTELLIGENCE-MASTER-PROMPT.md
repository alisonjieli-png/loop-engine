# Loop Engine self-orienting Code Intelligence and capability compounding mandate

Paste this complete directive into the development harness operating in the
current Loop Engine repository. Treat it as one execution mandate. Do not treat
its example names, paths, model IDs, values, thresholds, or third-party tools as
repository authority.

## 0. Required outcome

Research and bind to the live repository. Build a digest-bound orientation
snapshot. Audit the complete relevant source tree for behavior hidden in
literals, defaults, raw mappings, prompts, paths, providers, and duplicated
configuration. Correct representative high-value findings through the smallest
repository-native abstraction.

At the same time, continue the Reusable Capability Flywheel:

```text
solve expensive work
  -> verify and accept the task result
  -> observe a possible reusable implementation
  -> assess value, recurrence, risk, and overlap
  -> generalize and parameterize
  -> stage an immutable Code Intelligence candidate
  -> independently qualify the exact artifact
  -> explicitly promote the exact version and digest
  -> rebuild search projections
  -> retrieve a compatible future need
  -> execute and verify with zero model calls when exact deterministic reuse fits
  -> use bounded hybrid assistance only for a real semantic gap
  -> learn from accepted use and failure evidence
```

Do not stop at research, a prompt, a graph, finding counts, interfaces, YAML
moves, or test scaffolding. Continue through source changes, migrations,
focused tests, real runtime calls where configured, full verification, audit
deltas, and an evidence-backed report.

## 2. Preserve the live Loop Engine architecture

Revalidate these seeds against the exact working state before relying on them:

```text
Operational runtime type
└── Loop
    ├── Relationship
    │   ├── Starting
    │   ├── Spawned by
    │   ├── Queried by
    │   ├── Retrieved by
    │   └── Connected from
    ├── Role
    │   ├── Practitioner
    │   ├── Intelligence
    │   └── Solution
    ├── Versioned role profile
    ├── Mode
    │   ├── deterministic
    │   ├── hybrid
    │   └── non-deterministic
    ├── Step profile
    ├── Typed input and output contract
    ├── Loop and exit conditions
    ├── Budget, permissions, and effects
    ├── Model settings only when model use is authorized
    └── Run History
```

Hard rules:

1. `Loop` is the sole executable graph vertex and operational runtime.
2. Do not add `LoopNode`, role-specific runtimes, mode-specific runtimes, a
   semantic runtime, a graph runtime, a skill runtime, or a capability runtime.
3. Keep exactly three modes. Hybrid variations are typed assistance profiles,
   not new modes or subclasses.
4. A Canvas, Series, descriptive graph, catalog, queue, record, adapter, or
   passive resource has no execution mode of its own.
5. A model proposes. Deterministic authority validates, verifies, authorizes,
   and commits.
6. Candidate intelligence and code remain unavailable for production use until
   independent qualification and explicit promotion.
7. Search and graph projections are rebuildable. They are not lifecycle or
   identity authorities.
8. An exact reusable match completes with zero model calls. Do not use a model
   to confirm a sufficient deterministic match.
9. Reuse harvesting defaults to asynchronous execution through existing
   reactive scheduling. Inline execution is an explicit override.
10. Do not commit, push, merge, release, or publish without separate authority.

## 4. Build a digest-bound orientation snapshot

Self-orientation is a Development Assurance and control-plane operation. It is
not a product hot-path repository scan.

Produce a passive machine-readable snapshot containing:

- exact repository commit and full working-tree digest;
- package roots, public entry points, and runtime-version constraints;
- authority files with content digests and authority class;
- parsed classes, functions, methods, enums, assignments, and signatures;
- import, call, configuration-flow, and authority graphs;
- exact bindings for runtime, modes, roles, profiles, contracts, settings,
  lifecycle, catalog, reactive execution, model gateway, effects, prompts, and
  intelligence;
- enforcing checks and current consumers for every binding;
- duplicates, contradictions, assumptions, unknowns, and confidence;
- a targeted dependency digest set and invalidation policy;
- an identity digest that excludes generation time.

Required drift proof:

1. Build the snapshot twice without changes. Identity must match.
2. Change a controlled unrelated guide fixture. The working-tree digest must
   change, while semantic bindings remain fresh.
3. Change a bound authority fixture. The snapshot must become stale.
4. A normal product invocation must not rebuild or model-read the repository.

Operational orientation work runs through a canonical Practitioner Loop.
Parsing, hashing, and indexing are bounded deterministic implementation
primitives inside that Loop. Passive snapshots do not execute.

## 5. Evaluate descriptive code graphs without creating a second runtime

Prefer an existing configured CodeGraph for structural symbol, caller, callee,
path, and impact questions when it is fresh. If Graphify or another tool is
evaluated, treat it as one optional Code Intelligence producer.

```text
Descriptive graph
├── what source entities exist
├── how they are related
├── where each fact came from
├── whether the relation was extracted, inferred, or ambiguous
└── what may be affected by a source change

Executable graph
├── exact LoopDefinitionRef per executable vertex
├── typed ports and relationships
├── mode, conditions, budget, permissions, and effects per Loop
└── verification and Run History
```

Do not merge these planes.

### 5.1 Graphify research and execution rules

When Graphify is in scope:

1. Verify the official repository, package, version, commit, license, package
   dependencies, graph schema, query implementation, network behavior, logging,
   and benchmark harness from primary sources.
2. Pin an exact source revision in evaluation evidence. Do not depend on a
   moving pre-1.0 alias.
3. Install it in an isolated environment. Do not add its grammar set to the
   Loop Engine base dependencies for a trial.
4. Use `--code-only` for the structural proof. Remove provider variables from
   the process and disable query logging.
5. Write graph artifacts outside the Loop Engine repository unless a reviewed
   product decision explicitly admits them.
6. Use `.graphifyignore` to exclude generated output, saved evidence, local Run
   History, and structured records already governed elsewhere.
7. Measure cold and unchanged extraction time, peak memory, graph bytes,
   explicit entities, relationships, source files, implicit endpoints,
   confidence classes, and retries.
8. Test exact symbol, path, callers, callees, shortest path, and reverse impact.
9. Test free-form questions separately. Record over-expansion and truncation.
10. Treat implicit endpoints as unresolved external references, not extracted
    repository entities.
11. Bind every selected result to graph digest, repository state, query digest,
    traversal policy, source file, source location, adapter version, and
    truncation state.
12. Graph centrality, community membership, similarity, and confidence may
    propose context. They may not grant authority or select executable work.

Do not quote a memory benchmark as repository coding proof. Match dataset,
population, model, retriever configuration, evaluator, metric, and environment
before comparing results.

## 6. Run a whole-repository hardcoding audit

Audit the complete relevant repository, not only files expected to change.
Count and inspect:

- strings, numbers, booleans, nulls, and empty sentinels;
- function, method, dataclass, and model defaults;
- dictionary keys and fallback values;
- comparisons, match cases, statuses, modes, roles, actions, and events;
- paths, suffixes, environment names, URLs, provider and model IDs;
- timeouts, retries, backoff, leases, token limits, top-K, and thresholds;
- regex, SQL, commands, Docker images, queue names, and cache keys;
- prompts, instructions, rubrics, examples, schemas, and long text;
- allowlists, denylists, feature flags, rollout values, and aliases;
- structured YAML, JSON, JSONL, TOML, SQL, shell, CI, and package data;
- generated, vendored, benchmark, example, and saved-evidence surfaces.

Use AST or CST context, definitions, references, consumers, schemas, and
runtime traces. Do not count quotation marks with regex and call that an audit.

Each material finding records:

Classify findings as:

Not every literal is a defect. Matching text does not prove matching meaning.

## 7. Choose the smallest correct abstraction

Use this decision order:

1. Is it a constitutional, protocol, or security invariant?
2. Who owns its meaning?
3. Does it vary per call, run, profile, domain, tenant, deployment, or version?
4. Who may override it?
5. Is the value set closed or independently extensible?
6. Can it be deterministically derived?
7. Does changing it alter semantic identity or qualification?
8. Is it serialized or interoperable?
9. Is it sensitive?
10. Is it long-form material with its own lifecycle?
11. Does contextual semantic judgment remain after deterministic analysis?
12. Is the proposed abstraction more complex than the variation it supports?

Target matrix:

| Situation | Preferred owner |
|---|---|
| Varies per invocation | Typed required parameter |
| Usually stable, caller-overridable | Typed optional parameter with governed default |
| Shared behavior of one Loop profile | Versioned Loop profile setting |
| Governed choice across scopes | Versioned policy |
| Varies by deployment | Existing typed RuntimeSettings |
| Sensitive | Secret reference through approved resolver |
| Stable finite vocabulary | Enum, Literal, schema, or terminology authority |
| Independently extensible set | Existing registry, catalog, ontology, manifest, or entry point |
| Replaceable implementation | Strategy or realization binding |
| Computable | Deterministic derivation |
| Long prompt, query, mapping, or template | Versioned resource bundle |
| Contextual open-world choice | Bounded Intelligence Loop proposal |
| Clear private implementation detail | Intentional local literal |

Moving a value to YAML or `constants.py` is not an abstraction unless the new
owner has schema, type, scope, precedence, version, provenance, unknown-key
behavior, compatibility, security classification, and Run History visibility.

An invalid explicit value must not silently fall back. A provider SDK default

keys fail according to a versioned compatibility policy.

Preserve established callers through an explicit compatibility boundary. Do
not let compatibility input become a second authority.

## 9. Make prompts versioned semantic resources

Detect and correct:

- long inline runtime instructions;
- copied instruction blocks;
- opaque concatenation;
- f-strings mixing trusted instructions and untrusted data;
- output examples used instead of enforced schemas;
- branching hidden only in prose;
- unversioned composition order;
- model settings embedded in prompt builders;
- undocumented optional slots;
- prompt changes without regression evidence.

A prompt bundle declares:

```text
bundle ID and version
component IDs and digests
composition order
typed slots
sensitivity and trust class
escaping and size policy
omission behavior
slot provenance
trusted policy and untrusted data boundaries
output schema
interpreter profile
verification and abstention policy
render and slot-schema digests
```

Reject missing required slots and unexpected slots. Neutralize closing-delimiter
injection. Do not store raw secret slots in Run History. Do not load a prompt on
a deterministic path that needs no model.

Use the existing prompt and Context Intelligence boundary. Do not create a
second prompt registry.

## 10. Use Intelligence only for a real semantic gap

Deterministic order:

```text
exact authority mapping
  -> typed schema and data-flow analysis
  -> accepted history and prior decisions
  -> bounded deterministic heuristic with explanation
  -> Intelligence Loop proposal when policy permits
  -> deterministic validation
  -> abstain, request authority, or run a bounded experiment
```

Every Intelligence proposal contains:

- proposed value or classification;
- confidence;
- evidence references;
- assumptions and unknowns;
- alternatives;
- abstention and rejection reason;
- recommended validator;
- exact Loop profile, model runtime, prompt bundle, context, and policy identity.

Intelligence cannot override an explicit value, invent an authoritative key,
expand permissions or effects, select an ineligible capability, approve its own
candidate, or write trusted settings directly.

Repeated accepted decisions are candidates for a deterministic rule or profile
default. They still require independent qualification and promotion.

## 11. Preserve the Reusable Capability Flywheel

Online resolution:

```text
typed subtask need
  -> exact identity and contract lookup
  -> structured and lexical candidate generation
  -> optional graph and semantic projections
  -> hard lifecycle, contract, effect, permission, dependency, provenance,
     license, tenant, and qualification filters
  -> inspectable deterministic ranking
  -> exact parameter and adapter binding
  -> sandboxed execution
  -> independent output and effect verification
  -> accept or escalate
```

Hybrid assistance remains one mode with bounded stages:

```text
normalize then resolve
retrieve then rerank
adapt then execute
execute then diagnose
execute then repair
compose promoted capabilities
semantic body with deterministic shell
```

The model sees only a bounded eligible set or failure packet. It cannot revive
an ineligible candidate. Repair creates a new candidate version and never
mutates a promoted artifact.

Post-run learning:

```text
accepted verified result
  -> idempotent reuse observation
  -> asynchronous assessment
  -> original artifact preservation
  -> generalization and parameterization
  -> duplicate and overlap review
  -> candidate packaging
  -> independent exact-digest qualification
  -> explicit promotion
  -> projection rebuild
  -> warm zero-model invocation
```

The human-readable 1 to 10 score is advisory. Expected recurrence, cost avoided,
transfer breadth, contract clarity, determinism, testability, overlap, security,
effects, maintenance, build cost, and evidence diversity govern action.

## 12. Real provider and runtime authorization

This mandate authorizes bounded real provider calls for verification when a key
or approved secret reference is already configured.

Providers to inspect include Ollama or Ollama Cloud, OpenRouter, Mistral,
OpenCode Zen, OpenCode Go, and any repository-configured custom endpoint.

Rules:

1. Never print, persist, copy into source, place on command arguments, or include
   in Run History any raw key or authorization header.
2. Resolve keys from the current environment or approved local secret reference.
   A key supplied in a prior session may be recovered only from that local
   user-authorized session record and kept in process memory.
3. Do not claim a provider was tested because a key name exists.
4. Start with one physical call per provider and one exact model route.
5. Prefer current zero-price or included-quota routes. Record live pricing and
   availability separately from model quality.
6. Bind each call to an exact provider, model, route, source-backed maximum
   output, total-token ceiling, timeout, purpose, prompt digest, and validator.
7. Request the selected model's exact declared maximum. Do not replace it with
   an invented smaller default.
8. A run token ceiling may make a model with a larger exact maximum ineligible.
   Select another eligible model rather than silently truncating it.
9. For OpenRouter zero-price selection, require text output and the needed
   structured-output capability. Do not select an audio-output model because it
   advertises `response_format`.
10. Keep retry, same-provider fallback, cross-provider failover, format repair,
    evaluator repair, and task replanning distinct and separately authorized.
11. Stop after the configured physical-call budget. A rate limit, revoked key,
    invalid request, missing usage, or model mismatch is a real failure result.
12. Preserve provider-reported input and output usage. Unknown cost and usage
    remain unknown.

Minimum real proofs when available:

- one exact provider connectivity and output-contract probe;
- one typed prompt-resource call;
- one bounded Intelligence proposal followed by deterministic validation;
- one safe invalid-output or abstention path;
- one zero-model deterministic counterpart;
- current-key absence recorded honestly for providers that cannot run.

Real provider connectivity does not prove full product quality. A fixture does
not prove provider integration.

## 17. Anti-goals
