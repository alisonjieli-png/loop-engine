# Candidate review: compile a native material placement plan

Status: candidate only. No independent approval, installation, native-load test, or measured benefit.

- Original basis: first-party method drawn from the repository's native-placement research and general path-confinement reasoning. It does not copy a client guide or assert universal client paths.
- Facets: harness integrator or platform engineer; developer-tool company; per-step setup stage; exact client and version supplied at use time; model identity is not a placement rule.
- Search phrasings: "Where should these selected skills go for this coding agent version?"; "Plan the files for a fresh harness without overwriting another package."
- Typed input/output concept: `ApprovedItem[]`, `ClientLayoutProfile`, `WorkspaceScope`, and `EffectPolicy` to `PlacementPlan`, `Collision[]`, and `DiscoveryRequirement[]`.
- Effects: read-only plan. No file write, install, plugin activation, or protocol connection.
- Positive fixture: two approved skills have different native names and one relative reference each; the supplied profile maps skills to one project directory and task data elsewhere. Produce four distinct digest-bound paths plus isolation observations.
- Known-wrong fixture: two selected packages both claim native name `review`, and one resource path escapes with `../`. A plan that silently overwrites the first package or normalizes the escape into scope must fail.
- Nearest overlap and distinction: starter `package_one_skill_for_two_coding_harnesses` creates thin adapters for one tool. This method plans the exact placement of independently selected approved material for one fresh client instance, including collisions and resource confinement.
- Limits: current native layouts require versioned evidence and later observed loading; a correct plan does not prove client discovery. Review should challenge path normalization and unsupported file kinds.
