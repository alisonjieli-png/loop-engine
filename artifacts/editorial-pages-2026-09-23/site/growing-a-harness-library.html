Building Baltor

How we plan a larger harness library

A million files would be useful only if a harness could find a relevant package and use its exact contents. Here is what the count needs to represent.

Baltor · September 23, 2026 · 3 minute read

A developer looking for a procedure does not need a million results. They need one that fits the next step. We want Baltor's library to grow across instructions, skills, tools, reusable code and other files a harness can pick up, while keeping each selection small enough to inspect and use.

Count useful packages and files separately

A skill with an instruction page, a script and a schema contains three files but remains one method. Copies for different clients are delivery variants. A changed title, job label or model-specific wording does not create a new method.

We will need separate counts for candidate material, approved packages, active payload files and client renderings. A source directory can be large while the approved customer library is small. On September 23, the live release still holds 43 approved Markdown items. One million files is a growth goal, not the current inventory.

Start from tasks that need a method

Original procedures can grow from repeated work, verified code, missing search results and task descriptions that have a clear input and output. Occupation data can help identify needs, but changing a job title on the same instructions does not add coverage. The admission process should be able to return no new package when an existing one already fits.

Outside repositories and directories can identify useful work too. Their source, revision and file-level licence need review before copying or redistribution. The official Model Context Protocol Registry describes servers and where to find them; its entries are metadata, not a complete review of the code or remote service they name.

Source: The official Model Context Protocol Registry

Review the exact thing that will be delivered

Each proposed package needs its complete file list, exact digests, dependencies, allowed use and known failure cases. An independent reviewer should examine the scripts and configuration as well as the prose. Conflicting review decisions need an explicit resolution that names the version and the evidence.

If a file changes, the earlier review must not silently cover the new bytes. If evidence shows that a method fails within its stated scope, that finding must reach the same release and selection process that makes the package available. A successful model vote or a clean format check cannot erase a failed task.

Measure the library as customers experience it

A larger release needs tests for relevance, sensible no-result answers, complete downloads and native loading. It also needs a way to remove an item from future delivery while preserving the historical record. Adding files without those checks would increase the operator's work before it improved the customer's.

The first useful evidence is a small, reviewed release that a customer can search, load and use on a checked step. Growth should preserve that result at each larger size. We will report the count with its definition, release and limits.

Draft review gate

Update current catalogue facts and review the growth target before publication. Do not present candidates or rendered copies as served inventory.
