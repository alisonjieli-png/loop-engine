# Record the licence of every component you ship

Keep an accurate list of what you distribute and under which terms, so a licence question can be answered from a file instead of from memory.

## When to use it

Use it before any release that leaves your own machines: a package, a container image, a desktop program, a website bundle, or material a service hands to customers.

## Steps

1. List everything that goes out: your own code, direct dependencies, the dependencies they bring, fonts, images, data sets, models and sample files.
2. For each one, record the exact identifier of its licence, the version you ship and where the licence text came from.
3. Do not guess. If the licence is missing, unclear or dual, record it as unknown and treat unknown as a blocker, not as permission.
4. Check the obligations of each licence you ship: keeping a notice, offering the source, naming changes, restrictions on combining.
5. Produce the notice file the obligations require, and ship it with the release.
6. Keep the list in the repository beside the code, and regenerate it as part of the build, not by hand.
7. Compare the generated list with the previous release and review each difference.
8. Decide, once, which licence identifiers are acceptable for your product, and refuse the rest at build time.

## Checks

- Every shipped component appears in the list with an exact licence identifier.
- Unknown entries block the release rather than being treated as allowed.
- The notice file is present in the built artifact and matches the list.
- The list is regenerated by the build and is not edited by hand.

## Known-wrong example

A product ships a data set that was free to download. A customer asks for the terms. Nobody recorded them, and the page the file came from now says that commercial use needs a paid agreement. The product has been sold for two years. A recorded identifier at the time of first use, and a rule refusing unknown, would have raised the question before any money changed hands.

## What to record

- The component list with versions and licence identifiers.
- The obligations for each licence and how each one is met.
- The differences from the previous release and who reviewed them.
