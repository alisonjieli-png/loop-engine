# Generate complete original native candidates

The operator command `tools.generate_original_native_candidates` sends one
frozen task method to one explicitly selected model through `ModelGateway`.
It receives file text, computes digests and encodings itself, and calls the
existing native preparation factory. Nothing is approved, installed, staged
into a catalogue or published by generation.

## Existing owners

```text
Operational runtime type
└── Loop
    ├── Operational relationship
    │   ├── Starting
    │   ├── Spawned by
    │   ├── Queried by
    │   ├── Retrieved by
    │   └── Connected from
    ├── Role: Practitioner, Intelligence, or Solution
    ├── Versioned role profile
    ├── Purpose and domain categories
    ├── Run mode
    │   ├── deterministic
    │   ├── hybrid
    │   └── non-deterministic, with model-led semantic work
    ├── Step profile
    ├── Typed input and output contract
    ├── Loop condition
    ├── Exit condition
    ├── Graph relationships
    ├── Budget, permissions, and effect policy
    ├── Model settings when the selected mode permits a model
    └── Run History records
```

The command is operator tooling. Physical model invocations use the existing
gateway and its model Loops. Package data uses `CataloguePackage` through
`prepare_harness_candidates.prepare`. The local journal records one bounded
generation campaign; it is not a second intelligence catalogue, approval
store or executable runtime.

| Existing mechanism | Decision |
|---|---|
| `ModelGateway` and `ModelOutputAllocation` | Reuse route policy, exact provider capacity, physical attempt accounting and explicit output allocation. No direct model HTTP implementation. |
| `ProviderTokenBound` and `ProviderTokenBoundResolver` | Reuse when the operator requests a strict total-token ceiling. No prompt-length estimate is called a guarantee. |
| Native proposal factory | Reuse complete file trees, metadata validation, source pins, package digests and candidate-only output. |
| Review ledger | Its strict rows describe reviewers and verdicts, so generation does not mislabel drafts as review events. A small run-local dispatch/completion journal records generation, without a new catalogue engine. |
| Overnight journal | Its reader can skip torn lines and its local-model retry assumptions differ. Generation refuses a torn journal and holds an uncertain remote dispatch for reconciliation. |
| Existing atomic workspace writer | Reuse for the derived cursor. The immutable journal is the progress source; editing the cursor cannot authorize another call. |

## Plan, model answer and prepared package

The input is `original_native_generation_plan/v1`. It pins the checkout
revision, root licence and all opportunity-source digests. Each method has a
unique identity, specific input/output purpose, first-party authoring brief,
independent acceptance examples, native file inventory and metadata already
understood by the preparation factory.

The host fixes every path, media type, file role, effect, dependency and model
producer declaration. The model answers with only:

```json
{
  "record_type": "original_native_file_draft/v1",
  "method_id": "the_planned_identity",
  "files": [
    {"path": "AGENTS.md", "content": "Complete original instructions"},
    {"path": "reference.md", "content": "Complete supporting text"}
  ]
}
```

Every planned file must appear once. Extra fields, extra paths, missing
helpers, duplicate JSON keys, nonfinite JSON numbers and secret-shaped text
are refused. Only declared text formats can be generated by this command.
Binary generation needs a separately qualified mechanism.

Before the exact draft parser, each answer passes the existing
`model_response_admission` Loop with the draft's JSON Schema. Strict JSON is
tried first. The only permitted repair removes one exact enclosing Markdown
JSON fence, and the completion records it in `response_admission` with its
strategy and transformation. Text outside the fence, a second fence,
invalid JSON inside a fence and any key beyond `path` and `content` stay
refusals, reported as `draft_json_not_admitted`. The saved response keeps the
model's original bytes and digest.

The controller constructs `harness_candidate_batch_proposals/v2`. The factory
then produces `starter_catalogue_candidate_items/v3`, full package trees and
`candidate_intelligence_specifications/v3`. Exact duplicate package digests
under different method names do not add successful candidates. Near-duplicate
meaning, correctness and usefulness still require independent review.

## Call-limited subscription run

The initial production provider is Ollama Cloud. The exact model and its
family must match an existing committed gateway-reviewer installation in
`tools/candidate_review/resources/panel.json`; the command never guesses family
from a model name. The selected Ollama adapter owns credential discovery through
its existing local-only resolver, including its supported environment/file
sources. The generator checks presence through that adapter; it does not name or
read a credential environment variable itself. Presence does not verify that a
key works, and no provider probe or model-list request is made outside the call
ledger. A missing credential remains `provider_credential_unavailable`. The
command neither prints it nor copies it into a package. Any other provider
needs a committed provider binding, described next.

Use the exact plan digest reported by `sha256sum`. The following is an example
of the command shape, not authority to spend or a statement that it ran:

```bash
PYTHONPATH=src python -m tools.generate_original_native_candidates \
  --repository . \
  --plan artifacts/original-native-generation-2026-09-23/seed-plan.json \
  --plan-sha256 EXACT_PLAN_SHA256 \
  --output /approved/private/generation-run \
  --model glm-5.3 --family zhipu \
  --max-calls 10 --output-tokens 16384 \
  --allow-unbounded-total \
  --authorize-model-calls --authorize-writes
```

The explicit unbounded-total flag means there is **no strict total-token
ceiling**. Physical dispatches are bounded and each call has a source-backed
output capacity and the operator's explicit allocation. Total input/output
usage remains observed or unknown. Cost remains unknown unless separately
priced. Omitting `--output-tokens` requests the model's full known capacity;
an unknown capacity refuses generation.

One route and one physical attempt are requested. Automatic failover,
power escalation and generation retries are disabled. A provider outage is
recorded for resumption. A reported physical-call multiplicity violation stops
the run and remains in the journal.

## Committed provider bindings

`--provider-binding PATH --provider-binding-sha256 DIGEST` selects a custom
endpoint instead of Ollama Cloud. The file is
`original_native_generation_provider_binding/v1`, committed in this
repository. It holds exactly one custom provider in the settings file's own
shape, the trust anchor digest, the producer family, the path and digest of
a family evidence record (`generation_producer_family_evidence/v1`) and of a
capacity record (`endpoint_output_capacity/v1`), and the name of an operator
credential reference. It never holds a credential, a `credential_env`, or an
output maximum of its own.

Before any credential is read, the command checks the following:

- The binding, its trust anchor, both records and the review panel are
  committed unchanged at the plan's source revision.
- The provider is a verified HTTPS custom endpoint with purpose `generation`.
- `--model` and `--family` equal the binding's values exactly, and the
  family is in the review panel's vocabulary.
- Both records name the exact provider, endpoint and model.
- The capacity is known.

Only then is the credential reference resolved through
`tools/operator_credentials.py` inside this process, immediately before the
provider is built from `ProviderSettings.custom_endpoint`. The endpoint's
TLS trust contract (`tls_ca_file`, `tls_server_name`, `tls_pinned_sha256`)
refuses a server that cannot prove the expected identity before any request
is sent. The run stops on `tls_trust_refused`. A binding never falls back
to Ollama Cloud, and the family comes from its own evidence, never from an
unqualified reviewer added to the panel.

The first binding is
[Tactical's `gemma-4-coding-abliterated`](resources/original-native-generation-providers/tactical-gemma-4-coding-abliterated.json).
Its capacity is recorded as unknown, so the command refuses it with
`output_capacity_unknown`. The
[Tactical binding record](../docs/verification/TACTICAL-GENERATION-BINDING-2026-09-23.md)
lists the four server facts the owner must supply before a successor
capacity record can state a maximum.

## Optional strict total-token mode

Use `--token-ceiling` instead of `--allow-unbounded-total`, plus
`--token-bounds` and `--token-bounds-sha256`. The bounds file is
`original_native_generation_token_bounds/v1`, with a `bounds` array containing
the existing `ProviderTokenBound` fields. Every bound must identify the exact
provider request digest, model, route, maximum input and output counts, and
its qualified source and version. Qualification belongs to the host; supplying
a number is not evidence that it is correct.

The gateway checks exact-request bindings before transport. Missing or
incompatible bounds refuse the call. Unknown usage consumes the conservative
remaining reservation and stops a strict run. Reported usage exceeding the
remaining bound is recorded as a violation. The command never manufactures a
bound from character count or a semantic estimate.

## Resume and failure preservation

Run the same command with the same plan, implementation, model, family,
capacity, timeout and budget. The command verifies existing successful package
bytes and skips their model calls. The exact run configuration is immutable;
a different budget or source revision needs a deliberately new campaign.
The run contract is version six and the journal contract is version three.
Version six adds the draft admission contract to the provider binding
summary of version five, which is empty for the Ollama Cloud path. Journal
version three adds each completion's `response_admission` record. The run
binds the controller, native factory, preparer, ModelGateway, response
admission and selected provider adapter's direct source digests, plus the
shared prompt-bundle implementation. A bound run also binds the settings
modules that build its endpoint. The system prompt lives in the versioned
[`original_native_generation_prompt/v1` resource](resources/original-native-generation-prompt-v1.json).
Its exact resource bytes, bundle identity and rendered text digest are included
in `run.json`. It is loaded and frozen before the output run is opened; changing
it, including resource-only whitespace, refuses resume before another call.
The extracted version preserves the earlier 1,076 system-prompt bytes exactly.
Prompt semantic changes need a new reviewed resource version and a new campaign.
A completion binds the entire
prepared tree, including producer metadata, effects, specifications and reports,
and records the final physical attempt's reported model separately from the
gateway result's model field. Older runs remain historical and
are refused for resume; there is no automatic migration or field guessing.

Known completed failures are skipped by default. `--retry-failed` explicitly
permits another attempt of those failed methods within the remaining original
allowance. It does not repeat an interrupted or unknown dispatch. Unknown
dispatches require reconciliation before this run can proceed.

```text
Private run folder
├── run.json                 frozen model, plan, implementation and budget binding
├── journal.jsonl            flushed dispatch and completion events
├── cursor.json              derived progress, never approval or budget authority
└── method.attempt-N/
    ├── response.txt         bounded output, redacted when secret-shaped
    ├── proposals.json       complete native proposal when valid
    └── candidates/          factory output when preparation succeeds
```

Failed outputs stay beside successors. Records retain the original output
digest and the saved redacted-output digest separately. A malformed or
oversized response remains a failure; it is never replaced with canned content.
No generated script or test is executed by this command.

Prepared candidates require whole-package independent review, declared rights,
dependency/effect checks, native loading and task acceptance before any served
manifest can include them. A completed generation call establishes none of
those facts.

## Seed plan and verification

The [ten-method seed plan](../artifacts/original-native-generation-2026-09-23/seed-plan.json)
uses pinned O*NET task opportunities to suggest distinct bounded computation
methods. It includes matching, quota allocation, monotone fitting, deadline
and queue computation, a weighted statistic, sequence alignment, edit distance,
fixed-width parsing and three-valued logic. Each method names its nearest prior
advisory or concurrently authored package and the different contract. Those
relationships must still be independently checked for meaningful duplication.

The opportunity inventory retains its O*NET source and attribution. Generated
instructions are requested as original wording, without copying the source
task descriptions. The plan is not ten generated packages. Five real Ollama
requests are now preserved in the dated artifact directory: one timeout with
unknown usage, two output-limit failures, one duplicate-key JSON refusal and
one prepared seven-file MiniMax candidate. No generated implementation was
executed or admitted by those runs. Their four responses reported 39,465 tokens;
usage for the timed-out request and monetary cost remain unknown.

The separate [hundred-file plan](../artifacts/original-native-generation-2026-09-23/hermes-hundred-file-plan.json)
declares ten complete package requests and 100 planned payload paths. The user
selected Tactical Engineering's Hermes route for that campaign. The route is
now reachable under a verified TLS trust contract and serves one model,
`gemma-4-coding-abliterated`, but its output capacity is unknown, so no
generation request has run. See the
[discovery record](../docs/verification/TACTICAL-HERMES-PROVIDER-BINDING-2026-09-23.md)
and the [binding record](../docs/verification/TACTICAL-GENERATION-BINDING-2026-09-23.md).
Do not silently switch providers or count planned paths as generated files.

The plan is pinned to revision `9f7cd804`. After integration changes HEAD,
