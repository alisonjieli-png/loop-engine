What it does

Six things your agents get for each step.

Open one to see how it works and where the part behind it still has a limit. Point at a title, move to it with the keyboard, or press it.

  • A search returns short references, not whole files. Each reference tells your tool what the item is, where it came from, how large it is, its licence and the exact version. Your tool then downloads only the one it chose.

    A small step stops carrying the whole history. It carries the material it asked for, and nothing else.

  • Before a step writes new code, it can look for code that already does the job, and read that code's declared inputs, outputs and effects before choosing it. The choice between running existing code, a small model or a large model is recorded with the reason for it.

    The library on our server holds one example item today while a reviewed collection is prepared, so this works on your own material first.

  • Every model route says what kind of model it is, how large it is and where it runs. Each real call writes a cost record, and an unknown cost stays unknown instead of being written down as zero. That makes it possible to ask later which way of doing an operation was cheapest among the ones that were checked.

    Choose the model that fits the work, step by step, and keep the record of what each choice cost.

  • When a piece of work becomes something worth keeping, it can be written out as an installable package: the source, a command to run it, its tests, a container recipe, a cluster job file and a digest for every file. That package is then started in an interpreter that cannot load Baltor at all, so the claim that it runs on its own is something we carry out rather than something we say. The package refuses to hold a secret or a path from your machine.

    Take the package and run it. Nothing inside it points back at us.

  • A check can be wrong as well as the work it checks. When an independent check fails, Baltor first asks whether the work or the check is at fault, and every finding has to quote the evidence it rests on. The verdict is not given by the same process that produced the work.

    Using the outcome of past work to change what gets suggested next time is designed and written down. That part is not connected to a live run yet.

  • Long work gets interrupted: a restart, a full disk, a provider that stops answering. Baltor keeps reserving, pausing, saving a checkpoint and cancelling as four separate actions, so that picking work up again does not repeat something that already happened outside your machine. Each tool instance is started with a written assignment that names only the permissions that step holds.

    Hand a bounded step to a smaller model and let it work while you are away. The record tells you where it stopped and what it already did.

Do I need a model key to use Baltor?

No. A Baltor key gives access to permitted material. The model calls happen in your own tools, with your own provider account.

What happens to material I already downloaded?

It stays where you saved it. Revoking a key or cancelling stops new requests; it does not recall files that were already delivered.

Is there a free plan?

Can a team share one account?

        Technical runtime reference

        The public website calls a unit of work a step. The implementation uses the canonical Loop runtime described here and in the repository.

        Runtime classification and role profiles
        Complete behavior of a discrete cognitive or act step Loop node

        A discrete cognitive or act step Loop node is an independently governed instance of the Loop runtime responsible for one clearly defined cognitive step or action. A cognitive step might interpret information, identify a missing requirement, compare alternatives, or evaluate a result. An action might inspect a directory, build software, execute a test, create an artifact, or send an authorized email.

        Each discrete cognitive or act step Loop node receives the context, instructions, skills, plugins, tools, and working files relevant to its assignment. Essential information can be supplied directly, while additional information can remain in centralized storage behind authorized, versioned references. It does not automatically need the entire task history or every available tool.

        A separately initialized harness process, such as OpenCode, Pi, Codex, or a custom implementation, can perform the assignment. When explicitly permitted, another harness can attempt the same assignment after a failure. The assignment's contracts, permissions, history, and remaining authority persist across those attempts.

        Discrete describes the scope of the assignment, not a restriction to one attempt, one model call, or one output. A discrete cognitive or act step Loop node can examine whether an observation matches its expectations, identify a problem, repair or change its approach, and repeat until its declared completion conditions are satisfied.

        Alternatively, a discrete cognitive or act step Loop node can publish an initial candidate output and continue working while its continuation conditions and authority permit. It can produce additional alternatives over time, including alternatives that are better, worse, or useful under different circumstances. Consumers must identify exactly which output they used. Publishing an output does not necessarily mean that the producing assignment has finished.

        For externally consequential actions, continued operation does not authorize repeated effects. For example, generating alternative email drafts can continue, but sending an email requires its own authorization and protection against duplicate delivery.

        Harness Intelligence is a provisioning view over the four persistent layers. It is not a fifth persistent layer.

        Runtime Memory is the temporary note board for one run. Saving a note does not promote it into reusable intelligence.

        1. Install the local runtime

        Use the release and installation instructions supplied by your service operator. When installing this repository from an approved checkout, the serving dependencies are optional:

        python -m pip install '.[serving]'
loop-engine service --help

        The intelligence service can run locally or remotely. A remote model call still sends the selected context to that provider.

        2. Obtain service access

        Your operator creates a tenant and binds its access before issuing a scoped key, or binds your identity-provider subject. There is no automatic account creation from an unverified email address or a token's tenant claim.

        For Model Context Protocol clients, configure the endpoint shown in the workspace and supply its service token through your client's supported secret mechanism. Use the exact protocol version returned by the service. Do not put tokens in a URL, a shared Markdown file, or a checked-in client configuration.

        3. Bring your own model keys

        Keep model credentials on the machine or broker that performs the model call. Store only a secret reference in shared configuration. The browser workspace never asks for a model provider key.

        credential_ref: env:YOUR_PROVIDER_KEY
allow_network: false

        This is a configuration pattern, not an executable universal provider file. Use the selected adapter's documented schema. Enable network calls only after choosing the exact provider, model, task allowance, and disclosure scope.

        A native harness may use its own supported sign-in. A brokered tool can instead use a host-held credential on behalf of a scoped assignment. Neither arrangement removes the provider's terms, account limits, or required permissions.

        4. Verify the connection

        Connect to the workspace and confirm the tenant, namespace and scopes. Search for a permitted item. Inspect its identity, qualification basis and digest. Fetching a file does not prove that your harness loaded it or used it correctly.

        If access expires, reconnect with a valid token. If a download or checkout has an uncertain outcome, inspect its recorded state before repeating the operation. Do not assume a timed-out action was cancelled.

        Privacy and telemetry

        Do not include keys in prompts, intelligence bodies, screenshots, logs, or feedback. Embeddings and raw context are confidential data, not anonymous telemetry. Choose retention and improvement consent separately from execution access.
